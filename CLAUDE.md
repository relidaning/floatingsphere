# floatingsphere

Floating desktop monitor for Claude subscription usage and Claude Code sessions. Python, GTK4 via PyGObject, cairo drawing. Run: `python3 floatingsphere.py` (double right-click quits). User-facing overview in `README.md`.

## Visual mapping
- Center number: live Claude Code sessions (`len(collect_sessions())`).
- Outer ring: 7-day usage % (white tick = time elapsed in the week). Faint amber from 7d up to today's quota ceiling; the part of 7d past the ceiling is RING_HOT.
- Today's quota (`quota.py`): claude-maxer's daily budget (`~/.claude/state/claude-maxer-day.json`: `seven_start`, `budget` pp, `ceiling` %). If that file isn't today's (or its `seven_reset` differs by >60s; it's off by fractions of a second normally), the same split is computed here from maxer's `weekly_target` in its SKILL.md, held in-process for the day so `start` doesn't follow 7d. Hover card and web show it as a minibar right-aligned on the 5h meter's text line, not a row of its own: fill = % of today's budget spent since midnight (red past 100), tick = time of day. It shrinks to what the line leaves and is skipped under 20px.
- Water: height = current 5h window usage %; white rim ticks = time elapsed in the 5h window. Red while any session is `waiting` (a dialog or question to answer), else purple while any is busy, green when all are idle.
- Snapshot older than `STALE_S` (40 min) is drawn dimmed.
- Hover (after `HOVER_OPEN_MS`) opens `hovercard.py` in a `Gtk.Popover` (autohide off, so no grab): 5h/7d meters with a time-elapsed tick, sessions bar by status. No projection or "pace → N%": the user dropped it, since usage can't keep going at the same rate once it hits the limit. Animations are per-frame easing driven by the app's frame timer: `FPS` (24) while easing or while the card is open, `IDLE_FPS` (8) at rest, when only the ripple moves; `restart()` on open sweeps values in from zero.
- Left-click spawns `sphere_popup.py` (session cards → `focus_session()`; ■ → `stop_session()` on the second click (the first arms it, and it disarms after 3s); `+` → `claude_new.sh`). Both `+`s launch kitty through `kitty_group.sh`, which tabs the new window into the kitty group on the active workspace (every kitty is a group of one, so a real group of 2+ tabs beats a lone kitty even when that one is focused, since a phone launch happens with whatever was focused last; then the most recently focused), like dotfiles' `OpenTermGrouped.sh`: it focuses the group before launching so dwindle makes them neighbours, then `moveintogroup <dir>` (the only form Hyprland has), with cursor warps suspended. The new window is listed before dwindle tiles it, so the direction is taken only once its geometry has held still (a provisional position sent `moveintogroup` the wrong way); a miss is logged (`new: <project> kitty_group: …` in sphere-web's journal). No group there leaves it as its own (dotfiles rule `group set` for kitty). Toggling `group:auto_group` was tried; it joins whichever window dwindle opens on, and is global. `stop_session()` then also tries to close the kitty that our launchers opened: it finds the parent `zsh -ic '…$CLAUDE_NEW_LABEL…; exec zsh -i'` (checking its starttime against pid reuse) and signals it once claude exits. Terminals the user started themselves are left alone. SIGHUP does not work for this: `~/.zshrc`'s `TRAPHUP`/`TRAPTERM` (with `TRAPS_ASYNC`) keep the shell alive. SIGKILL does work. It is styled on the sphere/hover-card palette (glass surface, INK text, amber usage, `hovercard.STATUS` dot colors). Keep them in step.
- Web view: `sphere_web.py` (stdlib HTTP, port 8765, systemd user unit `sphere-web.service`) serves `web/` (a fixed whitelist in `STATIC`) + `/api/state`, and `POST /api/stop {id}` (two-tap ■ like the popup; the server resolves pids from `collect_sessions()` and never trusts pids from the client; a JSON body is required and a foreign `Origin` is refused, so other web pages can't trigger it). `POST /api/new {project, flags, prompt}` (the + sheet) starts one: `project` must be a name from `list_projects()` (dirs under `/data/apps` minus `NOT_PROJECTS`, recent first from `claude_new.sh`'s recent-dirs file; `claude_new.sh` keeps the same `NOT_PROJECTS` list for rofi, so edit both), `flags` are keys of `FLAGS` (the client never sends argv text), and it opens kitty through `systemd-run --user` in its own transient unit (otherwise it'd sit in sphere-web's cgroup and die on a service restart), with `--expand-environment=no` (systemd otherwise eats zsh's `${=…}`), and label/flags/prompt passed as env like `claude_new.sh`. Before launching, `trust_project()` sets `projects[path].hasTrustDialogAccepted` in `~/.claude.json` (what pressing y in the trust dialog saves; no CLI flag skips it), re-reading the file right before an atomic replace because every running claude rewrites it. It then waits (up to `NEW_WAIT_S`) for the new claude to register, matched by ancestry to the unit's kitty (`MainPID`; kitty moves its children into its own scope, so not by cgroup), and returns its `id`, so the page steps straight into its chat. Tapping a session opens a chat panel (`session_chat.py`):
  - `GET /api/chat?id&offset` returns transcript items from a byte offset (only whole lines, so a line being written is picked up next time) plus `dialog`. Dialogs come from the screen, because a pending permission prompt or AskUserQuestion isn't in the transcript until it's answered.
  - `POST /api/send {id,text}` bracket-pastes the text and presses Enter. It's refused while the session is `waiting`, since the text would pick options.
  - `POST /api/keys {id,steps}` sends whitelisted keys, digits and one-line text.
  - `GET /api/screen` returns the raw `get-text`.
  - `GET /api/commands?id` (`slash_commands.py`) lists what `/` offers in that session: a hand-kept `BUILTIN` list (Claude Code publishes none; update it when it adds commands), user/project skills and `commands/**/*.md`, synced org skills as `anthropic-skills:<name>`, and enabled plugins' as `<plugin>:<name>`. A lone `/word` in the composer shows them, narrowed per key (prefix, then word-start, then substring, then description). A tap fills `/name ` for arguments and keeps the keyboard up; on a hardware keyboard ↑↓ move, Tab completes, Enter sends, Esc hides it without leaving the chat. The list is capped at ~3 rows and shrinks with the space left, since iOS sizes the page as if the keyboard weren't there and a taller list pushed the composer under it.
  - A bare `/resume` sent from the composer isn't typed: claude's picker is a scrolling list (2 rows of 17 on a small window) the phone can't drive. The page opens its own sheet from `GET /api/resume?id` (`session_chat.list_resumable()`: the project's transcripts, newest first, title = custom-title / ai-title / first prompt, plus the last prompt; `claude -p` runs, whose first entry has `entrypoint` other than `cli`, are hidden like claude's own picker does). A pick POSTs `/api/resume {id,to}`, which only accepts an id from that list, only while idle, types `/resume <id>` (skips the picker) and waits for the registry's `sessionId` to follow. The session's id changes to the resumed conversation's, so the reply carries it and the chat reopens under it.
  - `/clear` (and `/new`, `/reset`) keeps the process but gives it a new `sessionId`. `sphere_web` remembers each id's `(pid, starttime)`s (`_procs`), so `successor()` names the id a session moved to: `/api/send` of a clear waits for it and returns `id`, and a 404 from `/api/chat` carries `moved` (for a /clear typed on the PC). The page's `followChat()` reopens the chat under it with a spinner instead of showing "ended".
  - Typing goes through kitty remote control. The dotfiles `kitty.conf` has `allow_remote_control socket-only` + `listen_on unix:${XDG_RUNTIME_DIR}/kitty-{kitty_pid}`, which only applies to kitty windows started after it. `find_window()` matches a session pid to a window by foreground process or ancestry.
  - Dialog shape (`parse_dialog`): numbered options under the bottom-most pure `─` rule that has a `1.` below it, up to the footer ("Esc to cancel"…) or the prompt box's named rule. A digit picks or toggles an option. Multi-select's un-numbered Submit row is reached with arrows from the `❯` cursor. For "Type something", send the digit, then the text, then Enter.
  - Claude Code's peer socket (`messagingSocketPath`) was ruled out: it delivers untrusted "messages from another session" and can't answer dialogs.
  - Self-update: the home-screen app never reloads on its own (iOS resumes the old page from memory), so `web_version()` (max mtime ms of `index.html`/`sw.js`) is stamped into the page (`/*PAGE_V*/0`) and sent as `v` in `/api/state`. A newer `v` makes `maybeReload()` reload at a safe moment: not with the + sheet or a dialog open, not while the composer is focused or a chat has a draft, and inside a chat only within 4s of the app coming to the foreground (the reload reopens it from `#<id>`, and re-stores the notification handoff so it still lands on the last message). Checked on leaving a chat, closing the sheet, every poll and on resume. On resume the SW also calls `registration.update()`. So edits to `web/` need no restart and no manual reopen.
  - The composer sits low: its bottom padding is the home-indicator inset minus 16px, and 6px while the keyboard is up (`.chat.kb`, set by `fitChat()`), since the inset is then under the keyboard.
  - Swipe-back is a touch handler on the panel plus `history.pushState`, so the phone's back gesture works too. The two must not both animate: iOS's edge swipe slides the page over its own snapshot of the list, and the panel following the finger as well showed two lists. So touches starting within `EDGE_PX` (24px) of the left edge are left to iOS, and a `popstate` the page didn't start (`ownBack`) opens/closes the chat without a transition.
  - iOS keyboard: `fitChat()` follows `visualViewport` only on whole-pixel changes and scrolls to the bottom only on `resize` (keyboard open/close), not on every iOS pan; `fitInput()` restores the list's scroll after its measuring collapse. Otherwise the conversation jumps while typing. A tap on the composer (iOS only) is focused by our own `touchend` handler: it sizes the panel for the keyboard first (height remembered from the last `resize`, `localStorage` `kbH`; before that, it lifts the box to the top for 120ms), so iOS finds the input in view and doesn't pan the page. That pan slid the header off the top until `fitChat()` snapped it back. While a chat is open `lockPage()` pins the body (`position: fixed` at its scroll offset, restored on close), and a `touchmove` on the panel that doesn't start in something scrollable is cancelled; iOS otherwise scrolls the list underneath (`overflow: hidden` doesn't stop it). The panel's `::before` backdrop also extends 100vh past its top and bottom, because when the keyboard opens iOS lifts the page before `fitChat()` catches up, which would otherwise show the list in the gap.
  - The canvas sphere is a port of `Sphere.draw` and the meters are a port of `hovercard.window_stats`, so keep them in step with the desktop versions. Deliberately a systemd service, not a container: it needs host `/proc`, `~/.claude` and signals to host pids, so a container would need `--pid=host`, a bind mount, uid 1000 and `apparmor=unconfined` (Docker's default AppArmor blocks the SIGTERM, and `stop_session()` swallows the `OSError`), and it measured slower and heavier.
- Phone notifications: Web Push to the home-screen web app, no third-party service.
  - `notify.py` is a `Notifier` thread in `sphere_web.py`. It polls `collect_sessions()` every 1s (a scan is ~0.1 ms) and notifies when a terminal session sits in `waiting` and on `busy`/`waiting` → `idle`. The user wants the messages to look grown-up (no emoji or symbols): the title is the session name, the body is a status line ("Awaiting approval" for a permission prompt, "Awaiting your answer", "Completed") plus one plain line of detail (the tool call or question from `parse_dialog`, or the start of the last reply), with markdown and terminal glyphs stripped by `plain()`. A status has to hold 3s first, and nothing else delays it: the user expects the phone to be about as quick as the water (a turn ending at 09:23:07 used to notify at 09:24:38). A 90s hold for sessions whose kitty window is focused was tried and dropped: the last-focused window stays focused, so the session in use was always the slowest. Sends are logged to the journal (`notify: <name>: <status>`). Headless sessions, and sessions already running when the service starts, never get one. Nor does a device whose app is open: each `/api/state` poll carries the page's subscription endpoint (`X-Push-Endpoint`), and `send_all()` skips an endpoint that polled within `ACTIVE_S` (8s). Going to the background POSTs `/api/push/away {sub}` so notifications resume at once. (iOS revokes the subscription after pushes that show nothing, so this is decided on the server, not by `sw.js` dropping the push.)
  - `webpush.py` does RFC 8291 encryption + VAPID with `cryptography` only (checked against `http_ece` and a real FCM round trip). The VAPID key is generated into `~/.config/floatingsphere/vapid-key.pem`. Replacing it invalidates every subscription.
  - Subscriptions are kept in `push-subscriptions.json` there. Endpoints must be on a known push service host (`PUSH_HOSTS`), so the server can't be used to POST anywhere else. 404/410 answers drop the subscription.
  - `web/sw.js` shows the push (tag = session id, so a newer one replaces the old one) and on tap stores `{id, at}` at `/pending-open` in Cache Storage (the page takes it on load/focus/visibility, because iOS drops `postMessage` to a suspended app and may open a closed one on `start_url`), then focuses the app and `postMessage`s, or opens `/#<id>`. A chat opened from a notification scrolls to the user's last message (`chat.toMine` → `scrollToMine()`), not the bottom. The 🔔 in the Sessions header subscribes: `GET /api/push` returns the key + HTTPS port, `POST /api/push/on|off {sub}`. The page re-posts `on` every time it opens, so the "Notifications enabled" push goes only to a new device (`webpush.add()` returns whether it was new).
  - Push needs a secure context, so sphere_web also serves HTTPS on 8766 with `~/.config/floatingsphere/tls-{cert,key}.pem`, a copy of besmart's mkcert cert (SANs 192.168.255.6, 192.168.1.8, localhost; expires 2028-09). Its root CA is already trusted on the user's iPhone. iOS only exposes PushManager in an app added to the home screen from the https address; the old http one can't subscribe. `Handler.disable_nagle_algorithm = True` is required: over TLS the headers and the body are separate records, and Nagle plus the client's delayed ACK held every response back ~40 ms locally (plain HTTP was 1 ms), more from the phone over the tunnel.
  - Telegram was tried first and rejected by the user: they want everything in their own web app.
- Weekly usage chart (web view only; the user asked for it in the app, not as a published page, and no notification about usage): `usage_history.py`'s `Recorder` thread in `sphere_web.py` folds the usage snapshot into `~/.config/floatingsphere/usage-weeks.json` every 60s, one period per 7-day window (`start`, `end`, `reset`, `peak`, `last`, `early`, `days` = running 7d % at each local day's end). A new period starts when `resets_at` moves by >1h, or when 7d falls by >`DROP_PP` (5) under the same `resets_at`: on 2026-09-28 Anthropic reset usage early (99% → 0%) and `resets_at` stayed on 10-01. Snapshots whose `resets_at` has passed are ignored. The first run backfills the current window from claude-maxer's log (`seven`, or "7d usage at N%" in `detail`); nothing older has a reset time, so it isn't used. `GET /api/weeks` serves the periods plus maxer's `weekly_target` (`quota.weekly_target()`); the page refetches it when the snapshot's `cached_at` changes. The chart (`renderWeeks()`) is a year board like GitHub's contribution graph, but a cell is a week: the last 52 7-day windows, laid out back from the latest `resets_at` in 7-day steps (a period joins the nearest one), in a column per month (the month the window ends in). Cell color = % of the limit the window used, 5 amber steps blended into the card surface (thresholds 25/50/75/95; full amber = 95%+, maxer's target); gray = no data; the running week has a white outline. An early reset's periods add up in their window (09-24 – 10-01 shows 99% + 96%). Below it a detail line names the tapped week (else this one); on a desktop, hovering picks the week. A first version drew a bar per week split into what each day added; the user couldn't read it (they took the gaps for day boundaries and expected 7), so don't go back to segmented bars.

## Data sources
- Usage: claude-maxer's snapshot `~/.claude/state/usage_snapshot.json` (`rate_limits.five_hour`/`seven_day` → `used_percentage`, `resets_at`; `cached_at`), refreshed every ~15 min by maxer's cron (`/data/apps/lidaning-skills/skills/claude-maxer/maxer.py`); re-read on mtime change.
- Sessions: `claude_sessions.py` reads Claude Code's registry `~/.claude/sessions/<pid>.json` (authoritative `status`: busy/waiting/idle; Claude Code adds new values over time, e.g. `shell` = turn over but a background shell still running, so `collect_sessions()` maps anything but busy/waiting to idle). **Don't go back to CPU-based busy detection** — the first version did (process-tree CPU ticks) and flickered purple on idle sessions whenever an MCP child or redraw spiked.
- Registry quirks: Claude Code's background daemon pre-warms `"spare": true` processes that register session files (skipped), and a session moved to the background keeps its terminal `claude --resume` next to the daemon worker under the same `sessionId`. `collect_sessions()` merges by `sessionId` and carries every pid in `pids`, so the count matches the agent panel and stop kills all of them.
- Stop also closes the kitty, but only one a launcher opened (`claude_new.sh` or the web +): `_launcher_shell()` recognises claude's parent `zsh -ic '…$CLAUDE_NEW_LABEL…; exec zsh -i'`. Once claude has exited, a non-daemon thread SIGKILLs the `zsh -i` it exec'd into (checking the start time so a reused pid is never hit), which closes the window. It's KILL, not HUP, because the user's `.zshrc` `TRAPHUP` runs the terminal-close fallback and doesn't exit. A terminal the user started claude in themselves is left alone.
- `claude_sessions.py`, `sphere_popup.py`, `claude_new.sh`, `rofi-claude-new.rasi` came from the retired waybar monitor in `/data/apps/dotfiles` (removed in its commit `02e0278`).

## Window placement (Hyprland)
- No layer-shell (gtk4-layer-shell isn't installed); window rules keyed on class `dev.floatingsphere` (popup: `dev.floatingsphere.popup`).
- The app sets rules at launch via `hyprctl keyword windowrulev2`, but `hyprctl reload` wipes runtime rules and the sphere then gets the user's border/shadow/blur and `inactive_opacity` 0.7 (a visible square) — so the static rules are also in dotfiles `hypr/UserConfigs/WindowRules.conf`. Only `move` stays launch-time (computed from the monitor size).
- `move` coordinates are **monitor-relative** and must account for monitor scale.
- Needs `nodim` + `opaque`: the user's config dims and fades inactive windows.
- Renderer: defaults to `GSK_RENDERER=cairo`. Measured against GL (NVIDIA): ~0.6% vs ~1% CPU, 26 vs 57 MB private RSS, 6 vs 20 threads.
- Hover focus: `follow_mouse = 1` would focus the sphere on hover, and the focus hand-back below then warped the cursor to the other window's center, so the pointer never stayed on the sphere and hover was dead. Fixed with `nofollowmouse`, plus the hand-back suspends `cursor:no_warps` around its dispatch.
- Focus: the user runs `input:float_switch_override_focus = 0`, so once a click focuses the (floating) sphere, hovering back onto a tiled window doesn't take focus back. `nofocus` is **not** a fix — it also stops pointer events (no hover, no clicks). Instead `on_active` dispatches `focuscurrentorlast` whenever the sphere becomes active.
- Testing hover: `hyprctl dispatch movecursor` alone sends no pointer enter; a real motion is needed (a python-evdev uinput device nudging REL_X works — `/dev/uinput` is user-writable).
